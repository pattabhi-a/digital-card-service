🎯 Core Capabilities

The Digital Card Service provides the following primary capabilities:

📄 PDF Generation

Generates secure, tamper-evident PDF digital identity cards with citizen biometrics, demographics, and security features.

🔐 Encryption & Security

End-to-end encryption of card data using Keycloak-integrated cryptography with tamper detection.

📤 Secure Distribution

Uploads encrypted cards to DataShare service for secure storage and retrieval.

📊 Status Tracking

Real-time card generation status (pending, generated, failed) with download links and error details.

🔄 Event-Driven Automation

Automatically triggers card generation on credential issuance via WebSub pub/sub events.

🔗 Identity Integration

Pulls citizen data from ID Repository and integrates with multiple MOSIP services.

🔌 REST API Endpoints

The service exposes a minimal REST API focused on card status and management:

GET /v1/digitalcard/{rid}
Retrieve digital card status and download URL for a registration ID
POST /v1/digitalcard/credential/callback/notifyStatus
Webhook endpoint for credential status updates (invoked by Credential Service)
POST /v1/digitalcard/idCreateEventHandle/callback/notifyStatus
Webhook endpoint for identity creation/update events (invoked by Registration Processor)
GET /v1/digitalcard/actuator/health
Kubernetes health check endpoint
GET /v1/digitalcard/actuator/prometheus
Metrics endpoint for Prometheus monitoring

Note: All endpoints require JWT authentication via Keycloak, except webhook endpoints which use WebSub signature verification.

📡 Event-Driven Architecture

Digital Card Service is fundamentally event-driven, listening to multiple event streams:

Event Topic Source Trigger Action
CREDENTIAL_STATUS_UPDATE Credential Service Credential is issued/updated Fetches credential data, generates PDF card
IDENTITY_CREATED Registration Processor Registration approved & processed Initiates credential request
IDENTITY_UPDATED Registration Processor Identity data is updated Regenerates card with new data
🔄 Event Subscription Model:
The service maintains WebSub subscriptions to event hub. On startup, it subscribes to all required topics. If subscription fails, it automatically retries every 1000 seconds with exponential backoff (max 3 retries).
🔒 Event Security:
All webhook events are verified using HMAC-SHA256 signature validation with shared secret. Only legitimate events from known sources are processed.

Integration Resilience

  • Retry Logic: Failed external calls retry up to 3 times with fixed delay
  • Timeout Handling: Service timeouts logged and reported; no circuit breaker currently
  • Error Recovery: Failed cards tracked; can be retried via database updates

🔐 Data Handling & Encryption

Data Flow

Security Features

  • End-to-End Encryption: Cards encrypted by KeyManager before DataShare upload
  • Signed PDFs: Card PDFs digitally signed with government certificate
  • Tamper Detection: Watermarks and security features prevent modification
  • Audit Trail: All card generation events logged with timestamp, user, status
  • PII Protection: UIN stored as salted hash; no plaintext personal data in logs
  • Optional Password: Card PDFs can be password-protected (configurable)

📈 Scalability Features

✅ Stateless Design: Service instances are stateless; all state in database or external services. Enables horizontal scaling with load balancing.
✅ Event-Based Processing: Decoupled from request/response. Multiple instances can process events independently without coordination.
✅ Database Transactions: JPA transactions ensure atomic updates; no data corruption on concurrent access.
⚠️ Limited Thread Pools: Fixed thread pools (size 2-5) may bottleneck under high load. Recommendation: Increase pool sizes based on expected throughput.
⚠️ No Caching: Hibernate L2 cache disabled. Every request hits database. Recommendation: Enable L2 cache for template and identity lookups.
⚠️ Synchronous PDF Generation: PDF generation blocks thread. High-volume scenarios may need async processing with task queue.

Current Capacity Estimates

  • Concurrent Requests: ~50-100 (with 5-thread pool)
  • Cards/Minute: ~30-50 (single instance)
  • Database Connections: Limited by Hibernate pool (no explicit config)
  • Horizontal Scale: Yes, instances are stateless
  • Recommended: Deploy 5-10 instances for production; use load balancer
