🏗️ Technical Patterns Synthesis

Architectural Patterns, Trade-offs & Design Decisions

Architecture Overview

The Digital Card Service follows a Layered Architecture with emerging event-driven patterns. This synthesis examines the architectural patterns in use, their effectiveness, and recommended modernization patterns.

Pattern 1: Layered Architecture

Current Implementation: Controller → Service → Repository → Database (see Capabilities)
✅ Strengths:
  • Clear Separation of Concerns: Each layer has distinct responsibility
  • Easy to Test: Services can be tested in isolation with mocked repositories
  • Familiar Pattern: Most developers understand layered architecture
  • Good for CRUD Operations: Well-suited for credential issuance workflow
❌ Weaknesses:
  • Tight Horizontal Coupling: Each layer depends on the layer below; cascading failures
  • Scalability Limits: Single instance bottleneck propagates through all layers
  • Synchronous Processing: All operations block until complete (no async capability)
  • Hard to Extract Services: Would require significant refactoring to split into microservices
Assessment: Good pattern for current scale (30-50 cards/min), but will require modification for 20x growth

Recommendation: Retain layered architecture, but augment with event-driven async patterns for PDF generation and bulk processing (see Scalability Blueprint)

Pattern 2: Event-Driven Architecture (Partial)

Current Implementation: WebSub pub/sub for credential status updates; 3 event topics (CREDENTIAL_STATUS_UPDATE, IDENTITY_CREATED, IDENTITY_UPDATED) (from Capabilities)
✅ Strengths:
  • Decoupled Services: Digital Card Service doesn't need to know about downstream subscribers
  • Scalable Event Distribution: Events can reach multiple consumers independently
  • Asynchronous Nature: Publisher doesn't wait for subscribers to complete
  • Audit Trail: All state changes recorded as events
❌ Weaknesses:
  • Partial Implementation: Only events are async; credential generation itself is synchronous
  • Sequential Event Processing: Events processed one-at-a-time; no batch processing (from Performance)
  • No Event Replay: If subscriber fails, events may be lost (no event store)
  • WebSub Reliability: Webhook delivery failures not handled gracefully
Assessment: Good foundation for decoupling, but underutilized for scalability

Recommendation: Extend event-driven patterns to:
  • Make PDF generation asynchronous (offload to task queue)
  • Implement batch event processing for bulk credential issuance
  • Add event store for audit and replay capability (see Modernization Patterns)

Pattern 3: Service Integration Pattern

Current Implementation: Direct REST calls to 6 external services (KeyManager, DataShare, Credential Service, etc.); synchronous blocking calls; no resilience
✅ Strengths:
  • Synchronous & Simple: Easy to implement and understand
  • Request-Response Clear: Can directly return results to caller
  • Standard HTTP: Works with any REST API
❌ Weaknesses (from Security):
  • No Timeouts: Requests can hang indefinitely if external service is slow
  • No Circuit Breaker: If KeyManager fails, entire credential issuance fails
  • No Retry Logic: Transient failures cause immediate errors
  • Cascading Failures: Service unavailability directly impacts card generation
  • Resource Exhaustion: Thread blocked during external call (small thread pools make this worse)
Assessment: Fragile; needs resilience hardening

Recommendation: Implement Resilience4J pattern:
@CircuitBreaker(name = "keymanager") @Retry(name = "keymanager") @Timeout(name = "keymanager") public String encryptData(String data) { ... }
Add timeout (5-10 sec), retry (2-3 attempts), circuit breaker (fail-open)

Pattern 4: Exception Handling

Current Implementation: Centralized @RestControllerAdvice with ApiExceptionHandler (from Code Quality)
✅ Strengths:
  • Centralized Logic: All exception handling in one place
  • Consistent Response Format: All errors return same JSON structure
  • DRY Principle: No exception handling duplicated across controllers
❌ Critical Issue (from Security):
  • HTTP 200 for All Errors: Returns 200 even for 400/403/500 errors (violates HTTP standards)
  • Breaks Client Handling: HTTP clients rely on status codes for error logic
  • Masks Failures: Makes debugging harder; logs don't show real status
  • Exception Swallowing: Stack traces not always preserved in response (from Code Issues)
Assessment: Good pattern, bad implementation

Recommendation: Fix to return correct HTTP status codes:
// Instead of: return new ResponseEntity(response, HttpStatus.OK) // Return: return new ResponseEntity(response, HttpStatus.NOT_FOUND) // Return: return new ResponseEntity(response, HttpStatus.FORBIDDEN) // Return: return new ResponseEntity(response, HttpStatus.INTERNAL_SERVER_ERROR)

Pattern 5: Caching Architecture

Current Implementation: Hibernate L2 cache DISABLED (from Performance)
✅ Strengths (of having cache, when enabled):
  • Reduces Database Load: Frequently accessed templates and identities cached
  • Lowers Latency: In-memory cache faster than network DB round trip
  • Built-in Solution: Hibernate L2 cache is standard pattern
❌ Critical Issue:
  • Cache Disabled: Every request hits database (no caching benefit)
  • High Database Load: 50-100 concurrent requests = 50-100 DB queries per operation
  • Performance Bottleneck: ~50% of latency due to repeated database lookups (from Performance)
  • No Cross-Instance Sharing: Even if L2 cache enabled, only works within single instance (no distributed cache)
Assessment: Quick win for performance improvement

Recommendation: Phased approach:
  • Phase 1 (Week 1): Enable Hibernate L2 cache with EhCache (local, single-instance)
  • Phase 2 (Month 1): Switch to distributed Redis cache (multi-instance shared state)
  • Expected Improvement: 50% latency reduction for identity/template lookups

Pattern 6: Deployment & Infrastructure

Current Implementation: Kubernetes + Helm (v1.3.0) + Istio; single replica; no auto-scaling (from Deployment)
✅ Strengths:
  • Modern Stack: K8s + Helm + Istio is industry standard for microservices
  • Good Foundation: Health probes configured, Istio routing ready
  • RBAC Configured: Proper authorization in place
❌ Weaknesses (from Deployment):
  • Single Replica: No high availability; single point of failure
  • No HPA: Can't auto-scale during load spikes; manual scaling only
  • Security Context Disabled: Container runs as root (privilege escalation risk)
  • No NetworkPolicy: Pod-to-pod communication unrestricted (network segmentation missing)
  • No Image Scanning: Docker images not scanned for vulnerabilities
Assessment: Good infrastructure pattern with critical HA gaps

Recommendation:
  • Deploy minimum 3 replicas for HA (from single replica → multi-instance)
  • Enable HPA with target CPU 70% (auto-scale to 5-10 replicas under load)
  • Add SecurityContext: runAsNonRoot, fsGroup, readOnlyRootFilesystem
  • Implement NetworkPolicy: deny-all, allow only required egress (to external services)
  • Add Trivy image scanning to CI/CD pipeline

Recommended Pattern Evolution

Short-term (1-2 months):
  • Fix exception handling (correct HTTP status codes)
  • Add service resilience (Resilience4J: timeouts, retries, circuit breakers)
  • Enable caching (EhCache L2)
  • Deploy 3+ replicas with HPA
Medium-term (2-4 months):
  • Make PDF generation async (event-driven)
  • Switch to distributed cache (Redis)
  • Implement batch processing for events
Long-term (4-6 months):
  • Consider extracting event-driven services (if load justifies)
  • Implement CQRS for read-heavy query patterns
  • Add saga pattern for distributed transactions with KeyManager/DataShare
