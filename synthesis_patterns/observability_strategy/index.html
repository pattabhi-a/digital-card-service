🔭 Observability Strategy

Monitoring, Tracing & Alerting for Production-Grade Operations

Observability Philosophy

Observability is the ability to answer arbitrary questions about system behavior without having to ship code changes. Three pillars support this:

  • Metrics: Quantitative measurements (requests/sec, latency, errors)
  • Logs: Textual records of events (who did what, when)
  • Traces: Request flow across service boundaries (what happened and how long)

Current State: Basic logging only; no metrics; no distributed tracing. MTTR: 30-60 minutes

Target State: Complete observability; proactive alerting; MTTR <5 minutes

Pillar 1: Metrics (Prometheus + Grafana)

Purpose: Quantify system behavior; answer "how much" and "how fast" questions

Key Metrics to Collect

Metric Type Purpose Alert Threshold
http_requests_total Counter Total requests by endpoint, method, status Alert if error rate >1%
http_request_duration_seconds Histogram Request latency (P50, P95, P99) Alert if P99 >5s
jvm_memory_used_bytes Gauge JVM heap memory usage Alert if >80% of max heap
jvm_threads_live Gauge Active thread count Alert if >90 threads (resource leak indicator)
db_connections_active Gauge Database connection pool utilization Alert if >80% of pool size
cache_hits_total / cache_misses_total Counter Cache effectiveness Alert if hit rate <70% (misconfiguration)
external_service_duration_seconds Histogram KeyManager, DataShare, Credential Service latency Alert if >2s (dependency issue)
kafka_messages_processed_total Counter Event processing throughput Alert if processing rate drops >20%

Implementation

# Add dependency: io.micrometer:micrometer-registry-prometheus @Configuration public class MetricsConfig { @Bean public MeterRegistry meterRegistry() { return new PrometheusMeterRegistry(PrometheusConfig.DEFAULT); } } # Expose metrics endpoint: /actuator/prometheus # Scrape interval: 15 seconds (Prometheus default)

Grafana Dashboards

Dashboard 1: Service Health
  • Requests/sec (by endpoint)
  • Error rate (by status code)
  • P50/P95/P99 latency
  • Pod restart count (indicates crashes)
Dashboard 2: Resource Utilization
  • JVM heap memory (% of max)
  • Active thread count
  • Database connections (% of pool)
  • Cache hit rate
Dashboard 3: Dependency Health
  • KeyManager response time
  • DataShare availability
  • Credential Service latency
  • Circuit breaker state (open/half-open/closed)

Timeline: 2 weeks | Cost: $8K

Pillar 2: Logs (Structured Logging)

Purpose: Provide detailed context for debugging; answer "what happened" questions

Current Issues

  • Sensitive data logged (passwords, API keys, PII)
  • Inconsistent log levels (some info, some debug)
  • No request correlation IDs (can't trace individual requests across service calls)
  • Stack traces logged without masking (exposes internal structure)

Structured Logging Setup

# Logback with SLF4J <configuration> <appender name="STDOUT" class="ch.qos.logback.core.ConsoleAppender"> <encoder class="net.logstash.logback.encoder.LogstashEncoder" /> </appender> <root level="INFO"> <appender-ref ref="STDOUT" /> </root> </configuration> # Log output (JSON format): { "timestamp": "2026-05-11T10:15:30Z", "level": "INFO", "logger": "DigitalCardServiceImpl", "message": "Card generation completed", "trace_id": "abc123def456", "card_id": "CARD-12345", "duration_ms": 1234, "status": "SUCCESS" }

Logging Best Practices

Principle Implementation Benefit
Request Correlation Add X-Request-ID header; include in all logs Trace request flow across services
Structured Fields Log as JSON with consistent keys (trace_id, user_id, action) Enable log aggregation and querying
Log Masking Redact passwords, API keys, PII before logging Comply with data protection regulations
Log Levels INFO: Important business events; DEBUG: Technical details; ERROR: Failures Appropriate verbosity for different contexts
Log Retention Keep 30 days in hot storage, 1 year in archive Balance cost with compliance requirements

Timeline: 1 week | Cost: $5K

Pillar 3: Distributed Tracing (Jaeger)

Purpose: Visualize request flow across services; answer "where is the latency" questions

Current Problem

When credential generation takes 5 seconds, it's unclear where time is spent:

  • 200-400ms: Fetch identity from ID-Repo?
  • 500-1000ms: Generate PDF?
  • 300-500ms: Encrypt with KeyManager?
  • 400-700ms: Upload to DataShare?

Without tracing, we guess. With distributed tracing, we know exactly which service is slow.

Implementation: Spring Cloud Sleuth + Jaeger

# Dependencies spring-cloud-starter-sleuth spring-cloud-sleuth-jaeger # Configuration (application.yml) spring: sleuth: sampler: probability: 1.0 # Sample 100% of requests (adjust for high volume) zipkin: baseUrl: http://jaeger-collector:9411 # Result: Automatic trace ID propagation # Every service call includes X-B3-TraceId header

Trace Visualization

Example trace for credential generation:

POST /cards (2000ms total) ├─ Validate request (50ms) ├─ Fetch identity from ID-Repo (300ms) ← External service ├─ Generate PDF (800ms) ← Async worker ├─ Encrypt with KeyManager (400ms) ← External service ├─ Upload to DataShare (350ms) ← External service └─ Update DB (100ms) Timeline shows which services are slow; enables optimization focus

Tracing Best Practices

  • Sample Rate: 100% for low-volume services (DCS: ~1K req/hour); 1-10% for high volume
  • Trace Retention: Keep 7 days in hot storage; query for debugging
  • Custom Spans: Add spans for business-critical operations (PDF generation, encryption)
  • Baggage: Propagate user_id, correlation_id to understand user-specific behavior

Timeline: 1-2 weeks | Cost: $6K

Alerting Strategy

Critical Alerts (PagerDuty/Slack Urgent):
  • Error rate >5% (indicates widespread issue)
  • P99 latency >10s (user-impacting slowness)
  • Pod restart loop (crash loop backoff)
  • Database connection exhaustion (connection pool >95%)
  • Memory pressure (JVM heap >90%; OOMKilled risk)
High Priority Alerts (Slack #alerts channel):
  • Error rate >1% (minor issues)
  • P99 latency >5s (noticeable slowness)
  • Cache hit rate <70% (cache misconfiguration)
  • External service latency >2s (dependency issue)
  • Message queue depth >5K (processing backlog)
Warning Alerts (Daily summary email):
  • Unusual traffic pattern (2x normal volume)
  • Certificate expiration <30 days
  • Disk usage >80%

Alert Implementation (Prometheus + AlertManager)

groups: - name: DigitalCardService rules: - alert: HighErrorRate expr: rate(http_requests_total{status=~"5.."}[5m]) > 0.05 for: 5m annotations: severity: critical summary: "Error rate >5% for 5 minutes" - alert: HighLatency expr: histogram_quantile(0.99, http_request_duration_seconds) > 10 for: 5m annotations: severity: critical summary: "P99 latency >10 seconds"

Timeline: 1 week | Cost: $3K
